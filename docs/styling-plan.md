## Принципы

1. **Ломаем сейчас, не потом.** Все переименования, зачистка токенов, перестройка классов — до публикации. После релиза каждый такой шаг = major.
2. **Простота стилизации > количество фич.** Если кейс «поменять кусок компонента снаружи» требует `!important`, хаков или селектора в кишки — это баг API, чиним.
3. **Правила, а не обещания.** Всё, что можно проверить в CI, — проверяется в CI.

## Фаза 0. Инвентаризация (1–2 дня)

Цель: знать масштаб, прежде чем двигать классы.

- [ ] Собрать список **всех** `var(--sg-...)` по `packages/react/styles/**/*.css`. Сверить с `tokens.css`. Выписать «чужие» имена (пример из аудита: `--sg-bg-elevated`, `--sg-border-color`, `--sg-box-shadow`, `--sg-item-hover-bg` в `mentions.css`).
- [ ] Собрать список **всех CSS-классов**, встречающихся в DOM компонентов (grep по `className=`). Разделить на:
  - кандидаты в «публичные» (корни, очевидные слоты);
  - кандидаты в «внутренние» (вспомогательные обёртки, модификаторы).
- [ ] Собрать список «магических значений» в CSS (hex-цвета, px-числа), которых нет в токенах.

Артефакт: `docs/_audit/styling-audit.md` (можно временный).

## Фаза 1. Нормализация токенов (0.5–1 день)

Цель: **один язык токенов** во всём пакете.

- [ ] В `tokens.css` остаются только документированные имена (см. `styling-contract.md` §3.1).
- [ ] Все «чужие» имена из компонентов либо переименовать под tokens.css, либо завести **алиасы** в `tokens.css` и перевести CSS-файлы на канонические имена.
- [ ] Убрать захардкоженные hex там, где есть токен (`#fff` → `var(--sg-color-bg)` и т.п.).
- [ ] Добавить недостающие токены для таблицы (`--sg-table-*`), списка (`--sg-list-*`), если в компонентных CSS они уже ожидаются неявно.

**CI-проверка (ввести в этой фазе):**

- [ ] Скрипт `scripts/check-tokens.mjs`: парсит все `var(--sg-...)` по `packages/react/styles`, сверяет с набором из `tokens.css`. Падает на неизвестных.
- [ ] Скрипт `scripts/check-no-important.mjs`: ищет `!important` в `packages/react/styles`. Падает при находке (с белым списком-исключений, если нужно).

## Фаза 2. Фиксация корней и слотов (2–3 дня)

Цель: **публичные классы** перечислены и проверяются тестами.

- [ ] В `styling-contract.md` §4 **заполнить** для каждого компонента: корень + слоты + компонентные токены.
- [ ] Переименовать или завести недостающие стабильные классы в DOM (если выяснится, что для слота нет класса вообще — добавить).
- [ ] Почистить DOM-дерево от лишних промежуточных `div`-ов там, где это не нужно для слотов (меньше узлов = меньше поверхностей для ломки).

**Тесты:**

- [ ] Для каждого компонента из §4 добавить минимальный тест: рендер с дефолтными пропами, в DOM присутствуют заявленные слотовые классы.
- [ ] Для сложных компонентов (`Table`, `List`, `Form`, `Tree`) — расширенные тесты: каждый слот присутствует в соответствующем состоянии (тулбар появляется при `searchable`, пустое состояние — при пустом `data`, и т.д.).

## Фаза 3. `classNames` / `styles` API (3–5 дней)

Цель: публичный API для точечной стилизации — ключ №2 для пользователя.

Приоритет реализации:

1. **Table** — самый сложный, бьёт в главную боль.
2. **List**.
3. **Form** / **Field**.
4. **Tree**, **Modal**, **Drawer**, **Tabs**, **Menu**, **DatePicker**.
5. Остальные по мере надобности.

Для каждого компонента:

- [ ] Тип `XxxClassNames` и `XxxStyles` с ключами из §4.
- [ ] Пропы `classNames?: XxxClassNames`, `styles?: XxxStyles` на компоненте.
- [ ] Пробросить классы/стили в соответствующие узлы DOM. Порядок: `class/style` библиотеки → пользовательские `classNames[slot]` / `styles[slot]` → `className` / `style` (эти два — только на корень).
- [ ] Тесты: каждый ключ доезжает до нужного узла.

**Параллельно:**

- [ ] Добавить `column.headerClassName` в `TableColumn` (паритет с `cellClassName`).

## Фаза 4. `prefixCls` — решение (0.5 дня)

Цель: убрать ловушку ожиданий (поле в `ConfigProvider` есть, эффекта нет).

Вариант A (рекомендуется по затратам): **убрать `prefixCls` из `SgConfig`** до того момента, когда будет реализован корректно. В доке — явная оговорка «изоляция классов через изолированный скоуп на хосте».

Вариант B (если нужен настоящий префикс): протащить `prefixCls` до конкатенации всех классов компонентов через утилиту `cx(prefix, part, modifier)`. Это задача уровня фазы, **не** делается попутно.

- [ ] Выбрать A или B, записать решение в `styling-contract.md`.

## Что НЕ входит в этот план (сознательно)

- Новые фичи таблицы (формулы, серверная модель, i18n для агрегатов).
- Визуальный редизайн компонентов.
- Миграция на CSS-in-JS / Tailwind / что-либо ещё. Текущая система (zero-runtime CSS + переменные) — фундамент контракта.
- Портирование на Vue/Angular. Контракт написан под React; портирование — после того, как контракт стабилен.
